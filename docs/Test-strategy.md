# Test strategy

## Цель

Проверить документированный REST-контракт для /auth, /booking, /booking/:id и /ping, включая позитивные потоки, обработку ошибочных данных, авторизацию и сохранение изменений.

## В объёме

- HTTP-коды и Content-Type;
- обязательность, типы и граничные значения полей;
- JSON и выборочные XML-сценарии из документации;
- фильтры firstname, lastname, checkin и checkout;
- доступ к существующим и отсутствующим ресурсам;
- cookie token и Basic Auth для изменяющих методов;
- CRUD-цепочки с повторным GET;
- очистка собственных тестовых данных.

## Вне объёма

Нагрузочное тестирование, длительная стабильность, глубокий security audit, конкурентные изменения одной записи и UI. Порог времени ответа не автоматизирован из-за публичного стенда и сетевой вариативности.

## Тест-дизайн

Использованы классы эквивалентности, проверки обязательных полей и типов, граничные даты, таблица решений для авторизации, переходы состояния create → read → update → delete и негативные варианты content negotiation.

## Оракул

Первичный оракул — официальная API-документация. Для HTTP-ошибок без явно описанного контракта применены стандартные семантики: 400 для невалидного запроса, 401 для ошибочной аутентификации, 404 для отсутствующего ресурса, 406 для неподдерживаемого Accept и 415 для Content-Type.

## Ограничения

Стенд общий и изменяемый. Результаты могут зависеть от чужих данных и сброса между запросами. Дата фактического исследовательского прогона: 2026-09-03 00:01 UTC.
